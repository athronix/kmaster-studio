### 🔑 第二个关键发现：「伪装硬编码」——比明文硬编码更隐蔽的债

|---|---|---|---|
| `--km-icon-bg` | ResourceCard:160 | `#f5f5f5` | 暗色模式下图标底仍是浅灰 |
| `--km-text-secondary` | ResourceCard:190 | `#888` | 次级文字不随主题变化 |
| `--km-highlight-bg` | LeftSidebar:906、SidebarSessionItem:312 | `rgba(255,215,0,.3)` | 搜索高亮不适配主题 |
| `--km-mono` | 11 处（settings/dialog 各处） | `ui-monospace` | 等宽字体族无法统一治理 |
| `--km-sidebar-bg` | LeftSidebar:659、SettingsNav:77 | `var(--km-panel)` | 侧栏底色无法独立调节 |

**为何历次审计漏掉**：审计口径是「查硬编码 hex」，而这类写法在人工目检时会被判为「已经用了 Token → 合规」，于是一路放行。

### 🔑 第三个关键发现：773 处原始 px —— 体量最大却最被忽视的债

历轮审计只盯**颜色**（hex/rgba），从未统计**字号与间距**。脚本口径扩展后暴露：`font-size` / `padding` / `margin` / `gap` / `border-radius` 中共 **773 处**直接写死 px，走 Token 的仅 0.6%。

**后果**：这正是用户所述「UI 反复完善却不系统」的物理根源——间距与字号无统一标尺，每个组件各写各的，视觉节奏永远对不齐；单点微调只能治标，改完这个页面那个页面又不一致。
**v2 对策**：必须建立 **spacing scale（4/8 基准）与 type scale**，并在实施计划中作为独立、可分批推进的阶段（不可与颜色治理混做，否则 diff 过大不可评审）。

### 🔑 第四个关键发现（架构师 T2.5 主挖）：Design Token「建而未用」

`font-size` 用 Token 仅 **2** 处 vs 原始 px **302** 处；`padding/margin/gap` 用 Token **3** vs 原始 px **471**。合计 **773 处原始 px，尺寸 Token 采用率 0.6%**。即 v1 §1.2/§1.3 的「间距/字号 Token」**在代码层等同于未实施**，也解释了 `unusedTokens=16`（其中 11 个是 font/space 类，定义了却没人用）。→ v2 已定为独立 P0（Spacing/Type/Radius Scale 三节）。

### 🧭 检索方法论沉淀：CSS 变量有 3 条合法注入路径

本轮「13 vs 8」之争的最终技术定论——查 Token 定义源，必须同时覆盖：
1. **SCSS 静态定义**（`variables.scss`）
2. **`setProperty('--x', …)`**（如 MarketLayout.vue:95 的 `--km-grid-cols`）
3. **响应式对象 + `:style` 绑定**（如 stores/layout.ts 的 `cssVars` computed → LayoutShell.vue:136 `:style="layout.cssVars"`，下发 `--km-left-w/-lh-w/-rh-w/-right-w`）

只查其一必误判。**主理人 14:48 的「13 个」正是只查了路径 1、2、漏了路径 3 所致**。此坑已固化进脚本（自动识别三类），且写入本项目检索规约。

**结论**：T2.5 = ✅ 验收通过。反虚高闭环（可执行脚本 + 干净基线 + 门禁 exit 码）已就位，成为本项目 UI/UX 验收唯一事实来源。

### 条目 10 — 发现脚本 `functionalEmoji` 数据层盲区（机制性缺陷）

**时间**：15:50 | **发现人**：主理人（复核 PM 的 `.ts` 发现时反查脚本）

脚本 `functionalEmoji` 只统计 `.vue` **template 字面量** emoji（报 43），对 `.ts` 数据层经变量插值渲染的 emoji **完全不可见**（真实 47 处，脚本报 0）。

**渲染链实证**：
```
constants/layout.ts:118  SETTINGS_CATEGORIES = [{ icon: '📊' }, …]  ← emoji 定义在数据层
   ↓
SettingsNav.vue:48       v-for="cat in SETTINGS_CATEGORIES"
   ↓
SettingsNav.vue:55       <span class="km-setnav-icon">{{ cat.icon }}</span>  ← 渲染成 UI
```

**风险**：若不修，下轮验收会报「功能性 emoji = 0 ✅」而设置页 12 个导航图标仍是 emoji —— **精确重现本项目历史上「验收通过但界面没改」的虚报模式**。反虚高机制本身出现了虚高漏洞。

**处置**：立为 T3a 前置阻塞项，派工架构师新增 `dataLayerEmoji` 指标后方可进入 T3b 计划编制。

### 条目 24 — `→` 改判 A 的连锁反应：机械数 ≠ 解释性数（217 vs 215）

**时间**：2026-08-07 · **性质**：裁定落地后的收口遗漏发现

#### A. 裁定

`SettingsDrawer.vue:77` `<n-button>更多设置 →</n-button>` → 改判 A（删掉 `→` 后「更多设置」完整通顺，不满足 B 类标准）。另两处（`NewTaskDialog:211`、`MemoryView:202`）保持 B。

#### B. 执行后的意外：机械数 217，不是 215

架构师把 `→` 加入 EMOJI_RE，但 **audit 是纯机械计数器，不应用位点级豁免**（豁免只在 verify 里工作）。`→` 三个位点全部被计数 → `functionalEmoji: 94 → 97`（+3 而非 +1）。

机械总数 `97+57+63 = 217`，解释性/可整改数 = `95+57+63 = 215`。

#### C. 收口方案

保持 `→` 在 EMOJI_RE 中（撤回就是开倒车），接受机械/解释性的双重口径：

- **审计器机械数：217** — 写入基线、门禁对照此数
- **实施计划可整改数：215** — 2 个类 B `→` 不进入整改
- **functionalEmoji 目标：97 → 2**（不是 → 0，因为 2 个 B 类不删）
- **其余指标目标不变**（`sfcScriptEmoji 57→0`、`tsEmoji 63→0`）

verify 的 E4 豁免已正确工作，闸门一二全绿。只需 `--write-baseline` + 实施计划数字对齐。

#### D. 方法论第 17 条（新增）

**机械审计与解释性判定的矛盾，是任何"自动化计数→人工判定"系统的固有张力。** 正则无法区分 `→` 是导航箭头还是句子连接符，强制执行字符级统一判定要么过度计入、要么过度豁免。**不要为抹平这个差距而让审计器"变聪明"**（给计数逻辑加豁免、加白名单、加上下文分析）——那会使审计器变成第二个人工判定工具，失去机械可复现的优势。

正确做法是承认两套口径并存，但只让**一套驱动自动化门禁、一套指导人工决策**：
- 门禁 = 机械数（客观、可复现、不可辩驳）
- 整改计划 = 解释性数（人工判定，需具名溯源）

并确保二者之间的差额**明确、有名字、可审计**（本轮差 2 = NewTaskDialog:211 + MemoryView:202，具名位点，E4 豁免登记在册）。

**累计方法论：17 条。**
